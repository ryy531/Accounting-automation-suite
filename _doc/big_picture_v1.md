## 0. 这份文档是什么

这是 ExampleCo 多业务自动化平台的**架构骨架**。它不讨论"做什么功能"，而是定义"怎么组织所有功能"，确保未来 1-3 年内：

- 接入新业务（公司税 T2、薄记、未知业务）不需要重构架构
- Alex 临时起意的功能追加 80% 不需要改代码
- bug 和易用性问题可以局部修复，不引发结构性改动

这份文档替代了之前的"Tax Automation 重构项目"思路。原"重构 send_package_email、合并 name_mapping 等"的阶段四/五**已搁置**——因为它们是基于"个税孤岛"假设做的抽象，在多业务平台架构下大概率切错刀。

历史项目简述（project_brief v1/v2/v3）和 ARCHITECTURE_REPORT 仍可作为**现状参考**和**领域知识来源**，但不再作为**未来方向**。

## 1. 业务全景

### 1.1 业务分两类

**A 类：提醒型业务**（已实现，本质是"按时间发邮件"）
- AR Reminder（应收账款）
- Annual Return Reminder（年度申报提醒）
- PST / GST Reminder（销售税提醒）
- T2 deadline reminder（公司税截止日提醒）

共性：扫一张表 → 找出该提醒的人 → 发邮件。差别只在话术、附件、触发条件。

**B 类：流程型业务**（有完整生命周期）
- 个税 T1（已实现完整流程，是最复杂的样板）
- 公司税 T2（流程未知，待与 Alex 梳理）
- 薄记 Bookkeeping（流程未知，待与 Alex 梳理）
- Payroll（独立业务，待梳理）

共性：客户从"未联系"经过多个状态最终到"已归档"，跨越数周到数月。

### 1.2 客户构成

- **公司客户**：每个公司客户可能同时购买 T2 + GST + PST + 薄记 + 老板个人 T1（套餐内）
- **散户个税**：单独的个人，不挂在任何公司下
- **联动场景**：公司客户的老板 / 配偶 / 子女可能同时是个税服务对象

### 1.3 终极目标

**所有自动化的最高优先级目标：帮 Alex 省时间。**
其次是规范化、可追溯、降本。这个排序在所有功能取舍时都成立。

## 2. 数据架构 —— 4 张核心表

```
👤 People (自然人)              ~500-1000 行
   ├─ 姓名、邮箱、SIN、出生日期、首选联系方式
   └─ 一个真实的人在系统里只有一行，永远

🏢 Companies (公司)              ~200 行
   ├─ 公司基础信息 + 商业关系字段（会员级别、月费等）
   ├─ 老板 → People（link to record）
   └─ 第二老板 → People

📋 Engagements (事项)            ~600-1000 行/年
   ├─ 类型：T1 / T2 / GST / PST / Bookkeeping / Annual Return / Payroll
   ├─ 关联对象 → People 或 Companies
   ├─ 状态、负责人、年度、due date、收费等
   ├─ ⭐ 状态机挂在这里（每条事项跑自己的状态机）
   └─ 所有业务流程的核心承载

📜 Events (事件流)               ~30,000-100,000 行/年
   ├─ 关联事项 → Engagements
   ├─ 类型：状态变更 / 邮件发送 / AI 调用 / 文件操作 / 客户回复 / ...
   ├─ 时间戳 + 描述 + 操作者
   └─ append-only，只新增不修改
```

### 2.1 关键约定

- **状态机挂在事项上，不挂在客户上**。"张三这个人现在到'待签字'"无意义；"张三的 2024 年 T1 申报到'待签字'"才有意义。
- **事项 ≠ 事件流**：事项是"待办"（一条记录跑几个月、状态会变），事件流是"历史"（一条记录就是一个动作、永不修改）。
- **事件流是当前 7 个 log.json 文件的合并升级版**。所有动作留痕，未来"客户投诉/审计/复盘"才查得动。
- **大量数据不会乱**：数据库 10 万行毫无压力；"乱不乱"是视图设计问题，不是表结构问题。

### 2.2 视图（产品自带，零代码）

不写代码靠视图过滤数据。常用视图举例：
- 今日待办（负责人 = 我 AND 状态 ∈ {待签字, 待付款, 待录入}）
- 积压清单（状态停留 > 14 天）
- 客户全景（点开某客户 → 所有事项 + 关联自然人 + 最近 20 条事件）
- 本周邮件流水
- AI 调用成本统计

每发现一种"我想这样看"的需求，就建一个视图。视图免费，不要省。

## 3. 系统架构 —— 3 层

```
┌─────────────────────────────────────────────┐
│  客户追踪系统层                               │
│  载体：NocoDB / Baserow（开源 + 自托管）     │
│  ├─ 4 张核心表（数据）                       │
│  ├─ 视图（看板、过滤、报表）                 │
│  ├─ Webhook（动作触发器）                    │
│  └─ ⭐ Alex + 员工的主要工作界面            │
└─────────────────────────────────────────────┘
                ↕ REST API + Webhook
┌─────────────────────────────────────────────┐
│  自动化层（Python）                           │
│  ├─ _lib/        （平台能力，所有业务复用）  │
│  ├─ business/    （每个业务的定义包）        │
│  └─ api_server.py（Flask Webhook 后端）     │
└─────────────────────────────────────────────┘
                ↕ 文件 IO
┌─────────────────────────────────────────────┐
│  共享文件夹（保留现有结构）                    │
│  客户文档、TaxCycle 文件、签字 PDF            │
└─────────────────────────────────────────────┘
```

### 3.1 部署：全部在公司局域网

- NocoDB / Baserow 自托管在现有 shared folder 服务器
- Python 自动化层运行在同一台服务器
- 数据从不离开公司，零月费
- 不需要 HTTPS / 域名 / 复杂认证（内网应用）

### 3.2 关于"Web 化"

**ExampleCo 不需要传统意义的 Web 化**。所谓"前端友好"已经被 NocoDB 网页 + Flask Webhook 自然解决：

- 看数据 / 改状态 / 看历史 → NocoDB 网页（产品自带）
- 触发动作（发邮件、跑 AI、批量操作）→ NocoDB 触发 Webhook → Flask 后端跑脚本
- 定时任务（每天扫描提醒）→ Windows Task Scheduler + Python

员工不再双击 .bat 选菜单，但平台也不是公网 Web 应用。是**局域网内的浏览器界面 + 后台自动化**。

## 5. 业务接入规范

每接入一个新业务，必须提供以下"业务定义包"：

| # | 内容 | 形式 | 用途 |
|---|------|------|------|
| 1 | 状态机定义 | 配置文件（YAML） | 状态列表 + 转移规则（含异常路径） |
| 2 | 专属字段 | NocoDB 网页配置 | 在事项表上扩展该业务专属列 |
| 3 | 触发规则 | 配置文件 | 状态变化 → 触发动作的映射 |
| 4 | 邮件模板 | docx / HTML 文件 | 用统一变量约定（Jinja2 风格） |
| 5 | AI prompt | 独立文本文件 | T1 解析、发票识别等业务专属 |
| 6 | 文件夹结构 | 配置文件 | 标准结构 + 历史别名 fallback |
| 7 | 入口动作 | Python 函数 | "开始一个新事项"按下后的步骤 |
| 8 | 计价规则 | 配置文件 | 提供给客户档案的商业关系字段 |

### 5.1 触发规则的三种模式（重要）

**默认 A，可升级 C，少用 B**：

- **A. 自动通知**：状态变化 → 给 Alex / Riley 发提醒，不自动执行
- **B. 自动执行**：低风险、可逆动作（移文件、写日志），直接跑
- **C. 自动准备 + 人工确认**：批量准备草稿 → 人审核 → 批量发送（涉及钱、邮件、对外通讯**永远走 C**）

不允许"全自动发邮件"或"全自动改 invoice"——这是底线。

## 6. 演化策略 —— 5 条原则

避免"易用性问题、bug、新增功能"触发结构性重构：

1. **schema 改在产品里，不改在代码里**
   加字段 / 改字段类型 = NocoDB 网页 5 分钟，0 代码改动。

2. **业务规则写配置，不写代码**
   状态机、邮件模板、AI prompt、触发规则 = 配置文件，代码只是"按配置跑"的引擎。

3. **新功能加新文件，不改老文件**
   老文件只做减法（删除冗余、提取共性）。新需求 = 新文件。避免历史上 send_package_email 1261 行膨胀的重演。

4. **接口稳定，实现可换**
   `_lib/` 提供的接口（ai_client.call、email_client.send 等）一旦定稳，业务代码都用接口。换 LLM、换数据库、换邮件服务 = 0 业务代码改动。

5. **每个动作留痕，事后可查**
   事件流表把所有动作记下来。bug 修复、客户投诉追溯、月度复盘——全靠事件流。

### 6.1 反向警告 —— 不要预先抽象

**只在某种需求出现 ≥ 2 次时才提取共性**：
- 第 1 次：硬编码
- 第 2 次：抽出函数
- 第 3 次：配置驱动

预先抽象 90% 是错的——想象的"未来需求"和真实的"未来需求"几乎不重叠。`_lib/ai_client.py` 是好例子：等到 5 处 Gemini 调用重复才抽出来，不是开始就规划。继续保持这个原则。

## 7. 与现有代码的关系

### 7.1 三类命运

| 类别 | 现有代码举例 | 命运 |
|------|------------|------|
| **基础设施（保留）** | `_lib/config/settings.py`、`logger.py`、`ai_client.py`、`email_client.py` | 完全保留，新系统直接用 |
| **领域知识（提取后复用）** | T1 解析 prompt、邮件模板、姓名解析规则、签字识别逻辑、B/B+ 匹配 | 脱离原脚本，作为函数库 / prompt 文件 / 配置存在 |
| **脚手架（替换）** | sign_pay_tracker.xlsx 维护、各 log.json、文件夹扫描循环、菜单式 .bat | 完全替换——这些是"没有 master 表的世界"被迫发明的代偿机制 |

**所以"完整重写 vs 部分复用"的真实答案**：基础设施保留 + 领域知识提取 + 脚手架替换。
